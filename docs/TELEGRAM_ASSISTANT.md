# AI Agent — ενιαία συνομιλία UI και Telegram

## Ενεργοποίηση ανά κατάστημα

Ο AI Agent ενεργοποιείται από τις ρυθμίσεις κάθε καταστήματος με το πεδίο
`ai_agent_enabled`. Η migration δημιουργεί το πεδίο ως `BIT NOT NULL DEFAULT 0`,
άρα όλα τα καταστήματα ξεκινούν απενεργοποιημένα.

Όταν είναι απενεργοποιημένος, UI και Telegram επιστρέφουν το κοινό μήνυμα
«Ο ΑΙ agent δεν είναι ενεργοποιημένος. Καλέστε στο {τηλέφωνο} για να ενημερωθείτε
για το κόστος ενεργοποίησης του.» (`AI_AGENT_CONTACT_PHONE`,
`app/assistant_messages.py`). Η κατάσταση επανελέγχεται ακριβώς πριν από την
πραγματική υποβολή.

## Ενιαία συνομιλία

Το πλευρικό office chat και το Telegram χρησιμοποιούν κοινά Gemini parsing,
deterministic validation, inbound/outbound ιστορικό, task/event logging, εκτέλεση
και απάντηση με πρωτόκολλο ανά ενέργεια.

Η κατάσταση ανοιχτού/κλειστού chat διατηρείται κατά την πλοήγηση. Στο UI οι
ταυτότητες εμφανίζονται ως `Εσείς`, `Εσείς · Telegram` και `erganiOS`. Το μήνυμα
του χρήστη εμφανίζεται αμέσως και κατά την ανάλυση ή εκτέλεση υπάρχει loading.

Στο **UI chat** το scope είναι το ενεργό κατάστημα. Στο Telegram φιλτράρονται
εργαζόμενοι όταν είναι γνωστό το κατάστημα.

## Επίλυση καταστήματος (Telegram)

1. Το μήνυμα φτάνει με `chat_id` → recipients που έχουν ήδη συνδεθεί με το κινητό
   (`/start 69…`).
2. Αν ο χρήστης έχει **ένα** κατάστημα με AI Agent → προχωρά με αυτό.
3. Αν έχει **πολλά** → αναζήτηση ονόματος στο μήνυμα (χωρίς τόνους / greeklish,
   π.χ. «Ερατο» → ERATO). Αν βρεθεί μοναδικό → προχωρά.
4. Αλλιώς → λίστα καταστημάτων («Επιλέξτε κατάστημα…»)· το αρχικό μήνυμα
   κρατιέται στο task (`clarification_kind=store_choice`).
5. Ο χρήστης απαντά με αριθμό ή όνομα → επανάληψη του αρχικού μηνύματος στο
   επιλεγμένο κατάστημα (ίδιο task, χωρίς νέο LLM για την επιλογή).

Reply με `focus_locked` (απάντηση σε προηγούμενο μήνυμα) κρατά το κατάστημα
εκείνου του μηνύματος. Ακόμη και **χωρίς** reply, το τελευταίο outbound με
`store_id` (π.χ. μετά από `today_info` στο Ερατο) κρατάει το κατάστημα — δεν
ξαναρωτάει λίστα. Ρητή αναφορά άλλου καταστήματος στο νέο μήνυμα υπερισχύει.

## Πλαίσιο συνομιλίας (κατάστημα και ονόματα)

Όταν στη συνομιλία έχει ήδη προσδιοριστεί **κατάστημα** και **όνομα/ονόματα**,
αυτά διατηρούνται ως `conversation_focus` μέχρι ο χρήστης να ζητήσει ρητά άλλο
κατάστημα ή άλλα ονόματα.

- **Reply** σε ειδοποίηση ή προηγούμενη εντολή: και τα δύο είναι δεδομένα.
  Σύντομες απαντήσεις όπως `Κλειστόν` ή `κλείσε κάρτα στις 17.00` εφαρμόζονται
  στους ίδιους εργαζομένους στο ίδιο κατάστημα.
- Χωρίς reply, το validation παίρνει το τελευταίο outbound μήνυμα που έχει
  `store_id` / `employee_afm` / ΑΦΜ στο κείμενο.
- Αλλαγή focus μόνο αν ο χρήστης ονομάσει άλλο κατάστημα ή άλλα πρόσωπα
  (αναζήτηση χωρίς τόνους, π.χ. `Μασούρα`).
- Ομαδικά κριτήρια («όσους τελειώνουν στις 15:30») δεν κληρονομούν τα παλιά ονόματα.

Οι today-alert και missing-punch ειδοποιήσεις γράφουν `store_id` και `employee_afm`
στο `karta_telegram_outbound_message`, ώστε το reply να έχει έτοιμο πλαίσιο.

Όταν το κατάστημα έχει **AI Agent = ON**, το Telegram κείμενο today-alert δεν
περιλαμβάνει σύνδεσμο `today-hit`· τελειώνει με «Απαντήστε στο μήνυμα για ενέργεια.»
Με AI Agent = OFF παραμένει «Προχωρήστε σε ενέργεια:» + URL.

## Gemini prompt (`parse_command`)

Πηγή: `app/telegram_assistant_service.py` → `_assistant_prompt_guide()` + payload.

Το μήνυμα προς το μοντέλο είναι JSON με:

| Πεδίο | Ρόλος |
| --- | --- |
| `role` / `guide` | Συμπυκνωμένες οδηγίες (όχι διπλότυπα philosophy/rules). Παραδείγματα είναι **ενδεικτικά**, όχι whitelist. |
| `now` | Τρέχουσα ώρα `Europe/Athens`. |
| `message` | Το κείμενο του χρήστη **ως έχει** (ελληνικά ή greeklish). |
| `reply_context` / `conversation_focus` | Προηγούμενο πλαίσιο, ανοιχτή διευκρίνιση. |
| `allowed_stores` / `allowed_employees` | Μόνο επιτρεπόμενα καταστήματα και **ενεργοί** εργαζόμενοι. |
| `today_home` | Πάντα — snapshot Αρχικής σήμερα. |

### Φιλοσοφία ονομάτων και διευκρινίσεων

- Φωνητική / μορφική αντιστοίχιση στο **Gemini**: `dionisi` / `διονυση` → ΔΙΟΝΥΣΙΟΣ,
  `fotopoulou` → ΦΩΤΟΠΟΥΛΟΣ/ΟΥ.
- Πολλά διακριτά επώνυμα («του Χ και του Υ») → όλα τα ΑΦΜ σε `employee_afms`·
  **χωρίς** «Εννοείτε…» ανάμεσα σε άσχετα πρόσωπα.
- Ίδιο ή παρόμοιο επώνυμο χωρίς διακριτό όνομα → `unknown` και ερώτηση
  «Εννοείτε του Χ ή του Υ;» + `ambiguous_employee_afms` (αποφασίζει το μοντέλο).
- Απάντηση σε `name_choice` δένει στο **ίδιο** `#N`· στέλνεται **ως έχει** στο
  Gemini με `pending_clarification` (υποψήφιοι + `preserve_*`). Δεν υπάρχει
  Python safety-net που να ξαναρωτά ή να «μαντεύει» ονόματα.

### Ακύρωση (`cancel_pending`)

- Νέο intent: σημασιολογική απόρριψη ανοιχτής εντολής/διευκρίνισης.
- Οποιαδήποτε διατύπωση (ακύρωσε, άστο, γάμα το, μην το κάνεις, #N…) — **όχι**
  σταθερό whitelist στο Python.
- Το runtime ακυρώνει ανοιχτά tasks (`needs_clarification` / `awaiting_ui_confirmation` /
  `awaiting_pin`) όταν το Gemini επιστρέψει `cancel_pending`, **ή τοπικά** για σαφείς
  φράσεις («άκυρο», «ακύρωσε», `cancel`) χωρίς κλήση Gemini.
- Μετά την ακύρωση η συνομιλία ξεκινά από μηδέν για πρόσωπα: outbound
  `assistant_cancelled` + `reset_conversation_focus` (κρατά μόνο `store_id`).
- Αν ακυρωθούν πολλές ανοιχτές, το μήνυμα αναφέρει πρώτα το **νεότερο** `#N`.
- Αν το σύστημα ρώτησε «να ακυρώσω;» και ο χρήστης πει ναι/ok, ακυρώνεται χωρίς
  νέο Gemini round όπου ισχύει.

### Ώρα κάρτας

- **Είσοδος/έξοδος (κρίσιμο):** `άνοιξε` / `open` / `clock in` → `card_check_in_*`·
  `κλείσε` / `close` / `clock out` → `card_check_out_*`. Το LLM δεν πρέπει να
  τα αντιστρέφει. Αν το intent διαφωνεί με ρητά ρήματα στο μήνμυμα, διορθώνεται
  στο validation (`app/assistant_card_intent.py`).
- «Άνοιξε/κλείσε την κάρτα» **χωρίς** χρονική ένδειξη → `*_now`, `time=null`.
- «πριν Χ λεπτά» / «Χ λεπτά πριν» → `*_retro` από το **τώρα** (`now − Χ`), ποτέ
  από την ώρα εισόδου/εξόδου της κάρτας. Offset από χτύπημα μόνο αν το πει ρητά
  («Χ λεπτά πριν την είσοδο/έξοδο»).
- Ρητή ώρα («στις 10», «στις 17:00») → `*_retro` με αυτή την ώρα. Δεν μαντεύει ώρα.

### `today_home` (πάντα)

Χτίζεται από `build_today_home_context` / `build_card_status_report()` σε **κάθε**
μήνυμα προς το Gemini (οι περισσότερες εντολές/ερωτήσεις αφορούν σήμερα), με
cache ~45 δευτερολέπτων ανά κατάστημα/ημέρα.

Ερωτήσεις όπως «ποιοι δουλεύουν στις 12» → intent `today_info` και η απάντηση
μπαινει στο `clarification_question` με βάση μόνο τα δεδομένα του `today_home`.

Δομή ανά εργαζόμενο (κενά πεδία κόβονται): `afm`, `name`, `status`,
`status_label`, `schedule_from` / `schedule_to`, `intervals`, `shift_type`,
`card_in` / `card_out`.

## Ανάλυση και πολλαπλές εντολές

Το Gemini επιστρέφει structured JSON με `commands[]`. Κάθε command έχει δικό του
intent, κατάστημα, εργαζομένους, ημερομηνία και ώρα. Ένα μήνυμα μπορεί να περιέχει
πολλούς εργαζομένους με ίδια ή διαφορετική ενέργεια, ημερομηνία και ώρα.

Αν υπάρχει ανοιχτό task σε `needs_clarification`, το επόμενο μήνυμα **δένει σε αυτό**
(όχι νέο `#N`), εκτός αν είναι ακύρωση **ή** ρητή αναφορά σε **άλλο** κατάστημα
(π.χ. ανοιχτή εντολή Training Room + «στο Ερατο…» → νέα εντολή ERATO).

Γενικότερα, όσο υπάρχει μη τερματισμένο task (`needs_clarification`,
`awaiting_ui_confirmation` ή `awaiting_pin`) **στο ίδιο κατάστημα**, κάθε επόμενο
μήνυμα αφορά την ίδια εντολή και ενημερώνει το ίδιο `#N`. Τα ήδη προσδιορισμένα
πεδία διατηρούνται και οι απαντήσεις συμπληρώνουν ή διορθώνουν μόνο την εκκρεμότητα.
Η ασάφεια είναι κατάσταση της υπάρχουσας εντολής και δεν μετατρέπει την ήδη
αναγνωρισμένη ενέργεια σε `unknown`. Μετά από **3 λεπτά** αδράνειας (`updated_at`)
οι ανοιχτές εντολές ακυρώνονται αυτόματα (`expired_idle`). Ρητή αναφορά
καταστήματος στο μήνυμα υπερισχύει του προηγούμενου conversation focus.

Όλο το batch παρουσιάζεται σε μία πρόταση και επιβεβαιώνεται μία φορά. Η εκτέλεση
γίνεται ανά command και εργαζόμενο και επιστρέφει ξεχωριστό πρωτόκολλο ή σφάλμα.

Υποστηριζόμενα intents:

- άνοιγμα/κλείσιμο κάρτας **τώρα** («άνοιξε/κλείσε την κάρτα» χωρίς ώρα),
- άνοιγμα/κλείσιμο κάρτας σε **σχετική** ώρα από το τώρα («πριν 10 λεπτά»),
- άνοιγμα/κλείσιμο κάρτας σε **ρητή** ώρα («στις 10», «στις 17:00»),
- άνοιγμα/κλείσιμο κάρτας βάσει ψηφιακού ωραρίου,
- αλλαγή ημερήσιου ωραρίου (`schedule_change` με `hour_from`/`hour_to`· αν το LLM
  επιστρέψει `unknown` ή λάθος label αλλά υπάρχουν από–έως + εργαζόμενος, ανακτάται
  αυτόματα),
- ρεπό,
- άδεια με συγκεκριμένο τύπο,
- **`today_info`**: απάντηση ερώτησης από το `today_home`,
- **`cancel_pending`**: σημασιολογική ακύρωση ανοιχτής εντολής/διευκρίνισης,
- `unknown` + `clarification_question` όταν κάτι είναι ασαφές.

Για εντολή βάσει ωραρίου η ώρα ανακτάται από την ίδια πηγή που χρησιμοποιεί η
Αρχική. Οι ISO ημερομηνίες μετατρέπονται στη μορφή `ΗΗ/ΜΜ/ΕΕΕΕ` του schedule.

Για χτυπήματα κάρτας ισχύουν οι ίδιοι κανόνες με την Αρχική / `work_card_guards`:
- **Έξοδος** μόνο αν υπάρχει είσοδος και **δεν** έχει ήδη δηλωθεί έξοδος.
  Όσοι έχουν ήδη κλείσει παραλείπονται με σαφή λίστα.
- **Είσοδος** μόνο αν **δεν** έχει ήδη δηλωθεί είσοδος κάρτας και **δεν** υπάρχει
  ανοιχτή πραγματική απασχόληση (ίδια εικόνα με την Αρχική).
  Όσοι έχουν ήδη ανοίξει παραλείπονται με σαφή λίστα.
- **Μελλοντική ημερομηνία ή μελλοντική ώρα σήμερα** απορρίπτεται
  (`Η ώρα κίνησης δεν μπορεί να είναι μελλοντική`) στο
  `new_card_punch_blocked_reason` και στο `build_wrk_card_se_payload`. Δεν είναι
  κανόνας του prompt, ώστε οι ερωτήσεις για ωράριο αργότερα σήμερα να απαντώνται.
- Σε ομαδικές εντολές, οι μη επιλέξιμοι βγαίνουν σε «Παραλείφθηκαν: …» και η
  πρόταση/επιβεβαίωση συνεχίζει μόνο με τους υπόλοιπους. Αν παραλειφθούν όλοι,
  η απάντηση είναι ενημερωτική (`answered`) χωρίς επιβεβαίωση προς ΕΡΓΑΝΗ.

## Επιβεβαίωση και πραγματική εκτέλεση

Στο UI το task δημιουργείται ως `awaiting_ui_confirmation`. Με το κουμπί
**Επιβεβαίωση** μεταβαίνει ατομικά σε `executing`, εμφανίζεται
`Εκτέλεση εντολών. Παρακαλώ περιμένετε...` και καλείται το ΕΡΓΑΝΗ.

Στο Telegram εμφανίζεται inline κουμπί **Επιβεβαίωση**. Το πάτημα ζητά τον
προσωπικό 4ψήφιο PIN. Ο σωστός PIN δεν αποθηκεύεται σε message/raw JSON/events,
μεταφέρει το task σε `executing` και ξεκινά την ίδια κοινή εκτέλεση. Μετά από
πέντε αποτυχημένες προσπάθειες το task κλειδώνει.

Οι υποβολές επαναχρησιμοποιούν τις υπάρχουσες ροές WRKCardSE, WTODaily και
WTOLeave, μαζί με authentication, listener routing, guards, persistence και
audit. Τελική κατάσταση task: `completed` μόνο όταν πέτυχαν όλες οι ενέργειες,
διαφορετικά `failed` με αναλυτικά επιμέρους αποτελέσματα.

```text
Εντολή #12:
HOXHA DASHURI · Επιτυχία · Πρωτόκολλο: AK-OP684763
ΒΗΧΟΣ ΙΩΑΝΝΗΣ · Επιτυχία · Πρωτόκολλο: AK-KAP431237
```

## Gemini / OpenAI και failover

```env
GEMINI_API_KEY=
GEMINI_MODEL=gemini-3.5-flash-lite
GEMINI_FALLBACK_MODEL=gemini-3.5-flash

OPENAI_API_KEY=
OPENAI_MODEL=gpt-5.5
OPENAI_TIMEOUT_SEC=20
OPENAI_STORE=0

# gemini,openai (default) · openai,gemini · ή μόνο ένα
ASSISTANT_LLM_ORDER=gemini,openai
ASSISTANT_RULE_FALLBACK_ENABLED=1

TELEGRAM_ASSISTANT_ENABLED=1
AI_AGENT_CONTACT_PHONE=ΧΧΧΧΧΧΧ
```

Parser: **Gemini** πρώτα (~1–2s). Αν αποτύχει → **OpenAI** Responses API
(`gpt-5.5`). Αν αποτύχουν και τα δύο → rule-based `today_info` για απλές
ερωτήσεις (ανοιχτές κάρτες / ποιοι εργάζονται).

Χρησιμοποιούνται συγκεκριμένα model IDs, όχι aliases. Το Gemini parsing έχει
σκληρό χρονικό budget (~8s). Το `today_home` κρατάται σε cache ~45s ανά κατάστημα.
Τα API keys δεν αποθηκεύονται στη βάση ή στο Git. Μετά από αλλαγή `.env`
απαιτείται restart / recycle IIS.

## Πίνακες και migrations

- `karta_telegram_inbound_message`: εισερχόμενα UI/Telegram και idempotency.
- `karta_telegram_outbound_message`: κοινό ιστορικό και Telegram message IDs.
- `karta_assistant_task`: payload, validation, LLM metadata και execution state.
- `karta_assistant_task_event`: append-only audit μεταβάσεων και αποτελεσμάτων.

```bash
python scripts/run_migration_store_ai_agent.py
python scripts/run_migration_unify_assistant_channels.py
```

## Ασφάλεια

- Άγνωστα Telegram chat IDs αγνοούνται χωρίς parsing.
- Gemini επιλέγει μόνο από server-side καταλόγους και η έξοδος επανελέγχεται.
- Ο κατάλογος `allowed_employees` περιλαμβάνει **μόνο ενεργούς** εργαζομένους του
  επιλεγμένου καταστήματος (`list_active_employees_for_store`, `karta_employment.active = 1`).
- Η εκτέλεση απαιτεί ενεργό AI Agent και επιβεβαίωση στο σωστό user/chat/store.
- Οι ατομικές μεταβάσεις αποτρέπουν διπλή εκτέλεση από διπλό πάτημα/retry.
- Καταγράφονται model, διάρκεια, usage, κανάλι, events, πρωτόκολλα και σφάλματα.

Η λειτουργία είναι production-writing: η επιβεβαίωση δημιουργεί πραγματικές
δηλώσεις στο επιλεγμένο περιβάλλον ΕΡΓΑΝΗ του καταστήματος.
